# InkHub 内容生命周期与行动工作台设计

## 1. 背景

当前 InkHub 将草稿、待审核、内容更新、处理失败和审核通过混在同一组文章状态中。工作台因此会把刚创建、仍在写作的草稿当作待办，内容库也能够完成工作台的大部分筛选与操作，两个入口职责重叠。

本设计将作者对文章成熟度的判断，与 InkHub 对审核和渠道交付的判断拆开。只有作者明确标记为“已就绪”的文章才进入审核与发布流程；内容库管理全部文章，工作台只指导用户下一步做什么。

## 2. 目标与非目标

### 2.1 目标

- 默认将所有未声明状态的 Markdown 文章视为草稿，避免误审核和误发布。
- 允许作者在 frontmatter 中明确将文章标记为已就绪。
- 用内容指纹判断当前版本是否已经审核和交付，不以文件修改时间作为事实依据。
- 让内容库完整呈现所有文章，并按内容阶段组织。
- 让工作台只呈现已就绪文章的下一步行动。
- 区分 Hugo 的按版本同步与微信公众号的一次性交付语义。

### 2.2 非目标

- 不根据标题、字数、元数据完整度或 AI 结果自动推断文章已就绪。
- 不自动把草稿批量改成已就绪。
- 不因文件修改而自动改写 frontmatter 中的内容阶段。
- 不把微信公众号建模为可以自动重复发布或覆盖既有文章的渠道。
- 本阶段不增加草稿协作、排期、访问量统计或内容日历。

## 3. 核心术语

| 术语 | 含义 | 来源 |
| --- | --- | --- |
| 草稿 | 仍在创作，不进入审核与发布流程 | frontmatter 缺省或显式 `draft` |
| 已就绪 | 作者确认文章可以进入审核与发布流程 | frontmatter 显式 `ready` |
| 待审核 | 已就绪，但当前内容版本尚未审核通过 | InkHub 推导 |
| 需要重新审核 | 已就绪，且当前版本不同于最近审核通过的版本 | InkHub 推导 |
| 可发布 | 已就绪、当前版本审核通过且不存在通用阻断问题 | InkHub 推导 |
| 渠道状态 | 当前文章在 Hugo 或微信公众号中的独立交付状态 | InkHub 交付记录 |

“已就绪”只表达作者意图，不表示文章已经审核通过。“可发布”是 InkHub 对当前内容版本的判断，不能写入 frontmatter 作为长期事实。

## 4. Frontmatter 契约

内容阶段使用现有 `publish` 命名空间：

```yaml
publish:
  status: ready
```

解析规则：

| frontmatter 值 | 内容阶段 | 行为 |
| --- | --- | --- |
| 字段缺失 | 草稿 | 只进入内容库 |
| `publish.status: draft` | 草稿 | 只进入内容库 |
| `publish.status: ready` | 已就绪 | 进入审核与发布流程 |
| 空值或其他值 | 草稿 | 只进入内容库，并显示字段警告 |

字段值使用小写 ASCII。展示层统一使用“草稿”和“已就绪”，不向普通用户展示内部枚举。

内容阶段以 Markdown frontmatter 为唯一事实来源。InkHub 可以在文章元数据编辑流程中写回该字段，但不能只修改数据库中的副本。作者在 Obsidian 中修改字段后，下一次扫描必须得到相同结果。

## 5. 正交状态模型

一篇文章同时拥有三组互不替代的状态。

### 5.1 内容阶段

- `draft`：草稿。
- `ready`：已就绪。

内容阶段由作者控制。草稿不产生待审核、待发布或重新同步任务。

### 5.2 审核状态

- 不适用：文章是草稿。
- 待审核：已就绪，且不存在当前版本的审核通过记录。
- 审核通过：已就绪，且审核通过记录绑定当前内容版本。
- 需要重新审核：已就绪，但最近审核通过记录绑定旧内容版本。
- 处理失败：当前审核或检查流程出现需要用户处置的失败。

### 5.3 渠道状态

Hugo 和微信公众号分别推导状态，任一渠道的状态不能覆盖另一渠道，也不能替代内容阶段或审核状态。

现有“已发表”和“已忽略”属于管理处置，不属于内容阶段。它们继续保留历史和筛选能力，但不能让草稿进入工作台或绕过审核发起新的渠道操作。

## 6. 内容版本判断

### 6.1 修改时间的职责

文件修改时间只用于快速发现“可能发生变化”的文件和列表排序。它不是审核或发布状态失效的依据。

扫描发现修改时间、大小或其他快速指纹变化后，必须重新读取文件并计算内容指纹。修改时间变化但内容指纹未变化时，不得让审核或渠道状态失效。

### 6.2 内容指纹的职责

内容指纹覆盖正文以及影响审核和发布结果的 frontmatter。审核记录、发布预览和渠道交付记录都绑定内容指纹所代表的内容版本。

状态判断遵循：

```text
当前内容指纹 = 审核通过指纹  -> 当前版本审核通过
当前内容指纹 != 审核通过指纹 -> 需要重新审核
当前内容指纹 = Hugo 交付指纹  -> Hugo 已同步当前版本
当前内容指纹 != Hugo 交付指纹 -> Hugo 需要重新同步
```

文章改动后又恢复为某个已审核版本时，只要内容指纹一致，可以恢复该版本对应的有效状态。系统不依赖单调递增的修改时间推断内容是否相同。

## 7. 状态流转

### 7.1 主流程

```text
草稿
  -> 作者设置 publish.status: ready
已就绪 / 待审核
  -> 当前版本审核通过
已就绪 / 可发布
  -> 同步 Hugo 或准备微信内容
已就绪 / Hugo 与微信分别记录交付状态
```

### 7.2 内容修改

```text
已就绪 / 当前版本审核通过
  -> 正文或相关元数据变化
已就绪 / 需要重新审核
  -> 新版本审核通过
已就绪 / 可发布
```

内容修改不会把 `ready` 自动改回 `draft`。作者仍然表达“这篇文章属于发布流程”，InkHub 只让旧版本的审核和按版本交付资格失效。

### 7.3 改回草稿

作者将 `ready` 删除或改成 `draft` 后：

- 文章立即退出工作台。
- 不能发起审核、Hugo 同步或微信准备。
- 既有审核、发布和人工确认历史继续保留。
- 再次改为 `ready` 时，根据当前内容指纹判断历史记录是否仍然有效。

## 8. 渠道规则

### 8.1 Hugo

Hugo 是按内容版本重复同步的渠道：

- 当前版本未交付：显示“需要同步”。
- 当前版本已经交付：显示“已同步”。
- 当前版本不同于最近成功交付版本：完成重新审核后显示“需要重新同步”。
- 当前版本同步失败：显示“同步失败”，进入工作台最高优先级行动。
- 文章不是已就绪或当前版本未审核通过：禁用同步操作并说明前置条件。

### 8.2 微信公众号

微信公众号是人工完成的一次性交付渠道：

- 未准备：允许为当前已审核版本准备内容。
- 已准备或已复制但未确认：准备结果绑定内容版本；内容变化后旧结果失效，需要重新准备。
- 已确认交付：作为文章级终态保留，不因后续内容变化自动生成重复交付任务。
- 已确认后用户仍可主动选择“重新准备微信内容”，但系统不得默认提醒或自动执行。
- 准备失败：仅在用户仍需完成本次微信交付时进入工作台。

微信已确认后的内容变化，仍可能触发重新审核和 Hugo 重新同步，但微信继续显示“已交付”。

## 9. 内容库设计

内容库回答“我有哪些文章”，必须包含当前工作区内所有已索引文章。

### 9.1 一级组织

- 全部。
- 已就绪。
- 草稿。

一级组织只使用内容阶段，避免将“已发布”错误地当作与草稿并列的生命周期。审核状态、渠道状态、管理处置继续作为筛选条件。

### 9.2 列表信息

每行至少展示：

- 标题和相对目录。
- 内容阶段：草稿或已就绪。
- 审核状态。
- Hugo 状态。
- 微信状态。
- 最后修改时间。
- 与当前状态对应的操作入口。

草稿文章的审核和渠道列显示“不进入发布流程”或等价的简短状态，不显示“等待审核”。非法 `publish.status` 在行内提供明确警告，但文章仍归入草稿。

### 9.3 内容库能力

- 搜索全部文章。
- 按内容阶段、审核状态、渠道状态、目录和 taxonomy 筛选。
- 查看和批量管理文章。
- 进入文章详情查看检查、元数据、历史和渠道结果。
- 保留现有管理处置，但处置不能改变 frontmatter 内容阶段。

## 10. 工作台设计

工作台回答“我现在应该做什么”，只读取已就绪文章，不提供全库搜索和批量管理的替代入口。

所有区段互斥。同一篇文章只出现在当前最高优先级区段，后端负责分组和去重，前端不得将多个分组自行合并后重复展示。

### 10.1 行动优先级

1. 审核或渠道处理失败。
2. 内容更新，需要重新审核。
3. 当前版本等待首次审核。
4. 当前版本审核通过，等待渠道交付。
5. 最新已就绪文章。
6. 最近处理记录。

### 10.2 最新已就绪文章

- 最多展示最近修改的 10 篇已就绪文章。
- 每篇只突出一个下一步主要动作。
- 已在更高优先级异常区段出现的文章不重复展示。
- 已进入最新列表的文章不再重复出现在最近处理记录中。
- 没有已就绪文章时，说明如何在 frontmatter 中设置 `publish.status: ready`，并提供进入内容库的入口。

### 10.3 下一步动作

系统根据状态为每篇文章选择唯一主要动作：

| 条件 | 主要动作 |
| --- | --- |
| 当前处理失败 | 重试或查看失败原因 |
| 当前版本不同于审核版本 | 重新审核 |
| 没有当前版本审核记录 | 审核文章 |
| 当前版本已审核且 Hugo 未同步 | 同步到 Hugo |
| 当前版本已审核且微信未交付 | 准备微信内容 |
| 当前版本无需继续处理 | 查看结果 |

当 Hugo 和微信同时待处理时，文章详情连续提供两个渠道动作；工作台仍只突出产品定义的首要动作，避免同一行出现多个主按钮。

## 11. 数据与接口边界

实现时至少需要表达以下事实：

- 文章解析后的内容阶段及原始字段是否合法。
- 当前内容指纹。
- 审核通过记录绑定的内容指纹。
- Hugo 最近成功交付绑定的内容指纹。
- 微信准备过程绑定的内容指纹。
- 微信是否已经完成人工确认交付。

API 向前端返回自然语言可映射的结构化状态，不能要求页面自行比较时间戳或拼接数据库状态。工作台分组、去重和优先级由后端统一计算，内容库通过独立字段筛选内容阶段、审核状态和渠道状态。

数据库迁移新增字段或表时，必须为每张表和每个字段添加数据库层面可见的 comment，遵守项目数据库脚本规范。

## 12. 迁移与兼容

- 升级后，所有缺少 `publish.status` 的文章默认归入草稿。
- 升级和扫描不得批量改写用户 Markdown 文件。
- 首次展示新模型时，明确说明已有文章默认按草稿处理，以及如何标记为已就绪。
- 已有审核、Hugo 发布、微信准备和人工确认历史继续保留。
- 文章后续标记为已就绪时，如果当前内容指纹与既有记录一致，可以恢复对应状态。
- 旧状态无法安全映射时采用保守策略：不允许发布，并给出重新审核或重新准备入口。

## 13. 异常与边界

- frontmatter 无法解析：文章保留在内容库并显示解析失败，不进入工作台。
- `publish.status` 非法：按草稿处理并显示修复提示。
- 扫描期间文件再次变化：使用源文件指纹冲突保护，不以旧内容更新状态。
- 审核期间内容变化：拒绝对旧版本审核通过，并要求重新加载。
- Hugo 预览后内容变化：旧预览失效，禁止确认交付。
- 微信准备后、人工确认前内容变化：旧准备结果失效。
- 微信已经人工确认后内容变化：不创建重复微信任务。
- 渠道未配置：不把“未配置”误报为文章处理失败，提供前往设置的入口。

## 14. 验证策略

### 14.1 后端测试

- 缺失、`draft`、`ready` 和非法 frontmatter 值的解析与持久化。
- 草稿不进入工作台，也不产生待审核和待发布状态。
- 已就绪文章按内容指纹正确推导首次审核和重新审核。
- 单纯修改时间变化但内容指纹不变时，审核与渠道状态保持有效。
- Hugo 交付版本失配时需要重新同步。
- 微信确认前版本失配时准备结果失效，确认后版本变化不产生重复任务。
- 工作台分组互斥、优先级稳定且最新列表最多 10 篇。
- 旧数据迁移保留历史且缺失内容阶段时默认草稿。

### 14.2 前端测试

- 内容库“全部、已就绪、草稿”分类和筛选。
- 草稿行不显示待审核或发布操作。
- 工作台不渲染草稿，并为每条文章显示唯一主要动作。
- frontmatter 状态非法、渠道未配置和空状态提示清晰。
- 内容修改后的审核、Hugo 和微信状态符合各自规则。

### 14.3 端到端流程

1. 新建无状态 Markdown，确认只出现在内容库草稿分类。
2. 添加 `publish.status: ready`，确认文章进入工作台并提示审核。
3. 审核通过，确认出现 Hugo 和微信交付入口。
4. 同步 Hugo、确认微信交付，再修改正文。
5. 确认需要重新审核；审核后 Hugo 需要重新同步，微信仍为已交付。
6. 只改变文件修改时间，确认不会触发重新审核或重新交付。

## 15. 验收标准

- 未明确标记为 `ready` 的文章永远不会进入工作台。
- 草稿不能发起审核或渠道交付。
- 已就绪不等于可发布，当前版本审核通过后才可以执行渠道操作。
- 内容版本通过内容指纹判断，修改时间不作为状态事实。
- 内容库能够找到全部文章并按草稿、已就绪组织。
- 工作台每条文章都有明确且唯一的下一步主要动作。
- 内容更新后审核与 Hugo 状态正确失效。
- 微信已确认交付后不会因内容更新自动产生重复发布任务。
- 现有历史数据得到保留，升级不会静默修改用户 Markdown 文件。
