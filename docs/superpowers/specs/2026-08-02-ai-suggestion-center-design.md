# AI 建议中心设计

## 1. 目标

将文章页现有的“AI Tag 建议”扩展为完整的“AI 建议中心”，覆盖 AI 返回的所有受支持元数据字段，并让建议生成具备可追溯的历史版本。

本功能遵循现有编辑模型：AI 建议永远只是草稿输入，用户采用后只修改页面中的元数据草稿，只有点击“保存到文章”才写回 Markdown。

## 2. 当前问题

- AI Provider 已返回 `description`、`category`、`series`、`slug`、`tags`，以及可能的 `keywords`，但前端只筛选并展示 `tags`。
- 当前建议 ID 由文章 ID 和内容哈希稳定生成，同一内容版本再次生成会触发 SQLite `UPSERT`，覆盖原建议集合并丢失原有采纳状态。
- 文章详情只返回最新建议，没有历史查询入口。
- 建议视图将所有值按字符串处理，数组类型的 `keywords` 无法可靠展示或采用。

## 3. 产品决策

### 3.1 建议与文章保存分离

- “采用”只更新文章页元数据表单草稿，不直接写源文件。
- “忽略”只改变当前页面的展示状态，不修改文章和 taxonomy。
- 用户通过现有“保存到文章”一次性写回全部草稿字段。
- 保存前继续展示字段级变更摘要；源文件发生变化时继续阻止保存并要求重新加载。

### 3.2 建议版本

- 每次生成创建一个独立建议版本，旧版本永久保留，作为可查询审计记录。
- 文章页默认只展示当前内容版本下最近生成的版本。
- 历史版本只读，不允许将过期建议直接采用到当前草稿。
- 当前内容哈希变化后，所有旧版本标记为失效；重新生成后才允许采用新版本。
- 生成失败不删除或覆盖已有建议，页面保留旧建议和错误提示。

### 3.3 支持字段

| 字段 | 建议类型 | 采用行为 |
| --- | --- | --- |
| Description | 单个字符串 | 替换草稿值，显示前后差异 |
| Category | 单个字符串 | 替换草稿值，使用 taxonomy 选择器的标准名称 |
| Series | 单个字符串 | 替换草稿值，使用 taxonomy 选择器的标准名称 |
| Slug | 单个字符串 | 替换草稿值，显示前后差异 |
| Keywords | 字符串数组 | 替换草稿数组，采用前显示完整列表 |
| Tags | 单个字符串（逐项） | 追加到草稿 Tags，大小写不敏感去重 |

不支持字段的 Provider 响应继续由 Application 校验并拒绝，不在 UI 中静默展示未知字段。

## 4. 数据与 API

### 4.1 SQLite

继续使用 `ai_suggestions` 现有表结构和 `created_at`、`updated_at` 字段，不删除历史数据。生成请求改用加密随机或时间加随机值生成唯一建议 ID，保留 Repository 的按 ID 更新能力供既有领域服务使用；正常生成不会再命中同一 ID 的 `UPSERT`。

Repository 增加：

- 按 workspace 和 article 查询建议版本摘要，按 `created_at DESC, id DESC` 排序。
- 按 workspace、article 和 suggestion ID 查询完整版本，防止跨工作区读取。
- 在事务中批量更新建议项的 `pending`、`accepted`、`ignored` 状态，保留原版本 JSON 供历史审计。

历史摘要至少包含：建议 ID、生成时间、内容哈希、模型、处理状态、建议数量和是否为当前内容版本。

### 4.2 HTTP 接口

保留：

- `POST /api/v1/articles/{id}/suggestions`：生成新版本，返回最新版本的完整建议。
- `GET /api/v1/articles/{id}`：文章详情继续返回最新建议，增加版本 ID 和生成时间。

新增：

- `GET /api/v1/articles/{id}/suggestions`：返回建议历史摘要，支持 `limit`，默认最近 20 个版本。
- `GET /api/v1/articles/{id}/suggestions/{suggestionID}`：返回指定版本的完整建议，只允许读取当前 workspace 下属于该文章的记录。
- `POST /api/v1/articles/{id}/suggestions/{suggestionID}/actions`：批量采用或忽略建议项，请求包含 `action` 和 `item_ids`；重复处理或文章版本过期时拒绝更新。

文章详情只返回最新版本中仍为 `pending` 的建议；历史版本返回全量建议，并为每一项标记 `pending`、`accepted` 或 `ignored`。建议项使用类型化值，字符串字段返回字符串，Keywords 返回字符串数组；Tags 仍拆成多个可单独采用的建议项。保留 `reason`、`new_term` 和 `usage_count`，不暴露 Provider 原始响应、Secret 或完整提示词。

### 4.3 生成并发与失败

- 同一文章可以连续生成；每个请求都有独立版本。
- 生成按钮在请求期间禁用，防止无意的重复点击；用户再次主动生成时允许创建新版本。
- 新版本保存失败时，旧版本仍可查询和使用；不返回部分写入结果。
- 历史查询失败不阻断文章编辑，显示可重试状态。

## 5. 前端交互

### 5.1 建议中心

`AISuggestions` 重命名为 AI 建议中心，按字段分组展示：Description、Category、Series、Slug、Keywords、Tags。每组显示建议数量，并支持组级“采用全部”和“忽略全部”；单项仍可独立采用或忽略。

采用状态只存在当前页面：

- 采用后显示“已加入草稿”，按钮禁用，避免重复追加。
- Tags 采用后追加到 MetadataForm 草稿，不覆盖已有 Tags。
- 其他字段采用后更新 MetadataForm 草稿，并在元数据变更摘要中显示。
- 忽略后隐藏该项，可通过“显示已忽略”恢复查看。

当前内容版本失效时，所有采用按钮禁用，并提示重新生成。生成完成后保持用户尚未保存的元数据草稿，不用 AI 返回值覆盖用户正在编辑的内容。

### 5.2 历史查询

建议中心提供“历史记录”入口，展示生成时间、模型、版本状态、建议数量和内容版本是否仍匹配。点击某条历史记录查看只读详情；历史版本不提供采用按钮，避免把旧内容建议误写入当前文章。

### 5.3 空状态与兼容

- 未生成时显示生成入口和“AI 只提供建议，保存后才写入文章”的明确提示。
- 未配置 AI 时保留现有配置入口，手工编辑不受影响。
- 旧 API 响应缺少版本字段时按单一最新版本兼容显示；旧建议 JSON 缺少数组字段时按空数组处理。

## 6. 模块边界

- Provider：只负责结构化返回候选，不负责持久化、采纳和历史。
- Editorial Application：负责字段类型校验、标准化、Tag 使用次数补全和建议版本构造。
- Suggestion Repository：负责版本持久化、按工作区隔离和历史查询。
- HTTP Runtime：负责鉴权边界、脱敏 DTO、路由和错误映射。
- React 页面：负责分组展示、草稿采用状态、历史查看和生成请求状态；不直接写 SQLite 或源文件。

## 7. 测试与验收

后端：

- 同一文章同一内容版本连续生成产生两条历史记录，旧建议项和处理状态不被覆盖。
- 生成失败保留旧版本。
- 历史列表按生成时间倒序并限制数量。
- 指定版本查询受 workspace 和 article 约束。
- Keywords 数组、Tags 拆项、字符串字段均能正确序列化和脱敏。

前端：

- 所有字段分组展示，Tags 不再是唯一可见字段。
- 各字段采用/忽略行为正确，采用只改变草稿，保存后才请求 metadata 接口。
- Tags 去重、Keywords 数组替换、字段差异摘要和失效禁用正确。
- 重复生成保留当前未保存草稿；历史入口可打开只读版本。
- 生成中禁用重复点击，失败可重试且旧建议仍可见。

回归运行 `go test ./...`、`go vet ./...`、前端全量单测、类型检查、lint 和生产构建；更新文章工作流 E2E 覆盖建议中心和历史入口。

## 8. 非目标

- AI 自动保存或自动修改 Markdown。
- 历史版本删除、清理策略和跨文章建议比较。
- 从历史版本恢复建议到当前草稿。
- 自动创建或修改 Hugo taxonomy term。
- 引入向量数据库、embedding 或新的召回服务。
