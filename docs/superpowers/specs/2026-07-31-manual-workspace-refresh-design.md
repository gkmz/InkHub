# 手动刷新工作区设计

## 目标

让用户在外部编辑器修改文章 frontmatter 后，可以在 InkHub 内主动重新扫描工作区，并立即看到文章阶段、审核状态和工作台行动队列的变化。

## 范围

- 工作台和内容库都提供“刷新工作区”按钮。
- 点击后由后端按当前工作区的目录规则重新扫描 Markdown 文件，更新文章索引。
- 扫描完成后，当前页面重新请求自己的数据；不会自动跳转、清空筛选条件或改变文章选择之外的页面状态。
- 工作台将“最新已就绪”作为第一组，其后保持“处理失败、内容已更新、需要审核、等待发布、最近处理”的顺序。

## 交互

- 空闲状态按钮文案为“刷新工作区”，使用刷新图标，并提供可访问名称。
- 扫描期间按钮禁用，文案为“正在扫描…”，避免重复提交。
- 扫描成功后提示“内容库已更新，共索引 N 篇文章”；失败后提示服务端错误，页面保留扫描前数据。
- 内容库刷新后保留搜索词、阶段筛选、审核筛选、处置筛选和已加载列表选择；重新加载首屏时移除已经不可见的选择。
- 工作台刷新后重新读取全部分组，保持服务端返回的排序。

## 后端设计

- 新增 `POST /api/v1/workspace/refresh`，受本机同源写请求校验保护。
- 端点读取最近使用工作区及其唯一 Source，复用现有 `buildSource` 和 `workspace.ScanWorkspace`，返回 `{indexed, failed}`。
- 扫描是同步请求；页面在请求未完成前显示进行中状态。
- 没有工作区、Source 配置损坏或 Provider 构建失败时返回现有错误格式，不修改文章列表响应。
- 不创建新的持久化状态或文件监听器；本功能只增加明确的手动同步入口。

## 排序规则

- 工作台后端分组顺序调整为：`latest_ready`、`failed`、`changed`、`needs_review`、`ready_to_publish`、`recently_handled`。
- 每组内部继续使用现有 SQL 排序，页面不自行重排。
- 草稿文章仍由后端排除，不能因刷新进入工作台。

## 验证

- Go HTTP 测试验证外部修改 `publish.status` 后调用刷新端点会更新索引阶段。
- 前端页面测试验证按钮发起刷新请求、显示进行中状态、成功后重新加载并提示结果。
- 工作台页面测试验证最新已就绪组位于第一组。
- 运行 Go 测试、前端类型检查、Lint 和 Vitest。
