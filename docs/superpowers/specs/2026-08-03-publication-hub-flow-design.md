# 审核中心与独立发布渠道设计

## 目标

将文章审核与渠道发布拆成清晰、可独立恢复的流程：内容库继续作为文章入口，审核页只负责形成可发布的文章元数据并完成审核；审核通过后，Hugo、微信公众号和小红书三个渠道分别进入自己的发布页面，互不阻塞，均可查看状态、历史和失败原因。

## 背景与当前问题

当前 `ArticlePage` 同时承载元数据编辑、AI 建议、审核、Hugo 目录选择、Hugo 预览和同步任务。Hugo 流程以内嵌区域追加在审核侧栏底部，导致：

- 审核完成后下一步不清晰，发布流程出现在页面最下方。
- Hugo、微信和小红书的入口被隐式串成单一路径。
- 文章已经发布到某一渠道时，其他渠道仍需要绕过当前主操作才能进入。
- Hugo 任务失败时页面只显示“同步失败”，缺少失败阶段和可执行处理动作。

## 设计原则

1. 内容库是唯一的文章主入口，打开文章先进入审核中心。
2. 审核和发布是两个不同阶段；审核页不嵌入长时间运行的渠道任务。
3. 三个渠道共享文章身份和审核门槛，但不共享执行状态或执行顺序。
4. 所有渠道操作必须可刷新恢复、可查看历史、可重试。
5. 已有旧文章按当前渠道状态进入，不要求重新发布已经完成的渠道。
6. 失败信息必须说明失败阶段、用户可理解的原因和下一步动作。

## 信息架构

```text
内容库
  └─ /articles/:id                 文章审核中心
       ├─ 元数据、AI 建议、检查结果
       ├─ 审核通过
       └─ 发布渠道状态入口
            ├─ /articles/:id/hugo          Hugo 同步
            ├─ /articles/:id/wechat        微信内容准备
            └─ /articles/:id/xiaohongshu   小红书图片集
```

### 审核中心

审核中心保留文章预览、元数据表单、检查结果、AI 建议中心和审核历史。审核页顶部增加紧凑的“发布渠道”区域：

- 审核未通过时，三个渠道显示锁定状态和“审核完成后可用”。
- 审核通过后，三个渠道立即显示为独立按钮或状态行。
- `尚未处理` 显示“开始”；`处理中` 显示进度；`已完成` 显示“查看”；`失败` 显示“查看原因/重试”；`未配置` 显示“去设置”。
- 审核页不再渲染 Hugo 目录选择、预览和同步组件。
- 审核通过后不自动跳转到任何一个渠道，避免把 Hugo 错误地当作必经步骤。

### 渠道页面

三个渠道页面使用一致的页面骨架：文章标题和审核状态、渠道切换导航、当前渠道主流程、当前渠道历史和返回审核中心。渠道切换导航只切换目标渠道，不重置已经提交的任务。

- Hugo 页面负责目录选择、生成预览、检查、确认同步和恢复任务。
- 微信页面负责模板选择、图片准备、HTML 预览、复制和人工确认。
- 小红书页面负责 AI 草稿、人工编辑、移动端模板预览、图片集导出和人工发布记录。

每个渠道页都显示其他两个渠道的入口；渠道未配置时入口保持可见但显示“去设置”，而不是隐藏导致流程不可发现。

## 状态模型

审核状态与渠道状态分开维护。审核状态只决定渠道是否允许开始，不会替代渠道状态。

### 渠道状态

```text
blocked       审核未通过，不能开始
not_configured 渠道未配置
ready         已审核，可开始
running       任务运行中
completed     当前文章版本已完成
failed        最近一次任务失败，可重试
stale         文章内容或元数据更新，需要重新处理
```

前端可将现有后端自然语言状态映射到上述展示状态，但不改写已有数据库语义。渠道完成后再次打开页面必须显示最后一次结果和历史；文章更新时只将受影响的渠道标记为 `stale`，不会清除旧的成功记录。

### Hugo 任务状态

Hugo 内部任务仍保留现有 `preparing`、`delivering`、`published` 等状态。审核中心只展示渠道摘要，Hugo 页面展示详细阶段：

```text
检查发布前条件 → 生成发布预览 → 等待确认 → 更新博客文件 → 完成
```

失败响应需要包含：

- `stage`：失败阶段，例如 `preflight`、`prepare`、`deliver`。
- `code`：稳定的错误代码，用于前端决定是否显示重试或设置入口。
- `message`：面向用户的原因。
- `action`：用户下一步可以执行的动作。
- `retryable`：是否允许直接重试。

现有 API 未提供这些字段时，前端保留兼容解析，并将通用错误显示为“请查看发布历史”；后端补齐字段后自动展示详细诊断。

## 数据流与恢复

1. 内容库打开文章，审核中心读取文章详情和独立渠道摘要。
2. 用户保存元数据后点击“审核通过”，审核接口完成原子写回并更新审核状态。
3. 审核中心重新读取渠道摘要，三个入口同时解锁。
4. 用户进入任意渠道页并发起操作；请求使用文章当前内容版本和对应 Provider。
5. 渠道任务通过文章级工作流接口恢复，刷新或重启不会丢失运行状态。
6. 渠道失败只更新当前渠道，不改变其他渠道状态。
7. 文章内容版本变化时，相关预览和草稿变为过期；旧历史保留并可查看，但不能确认交付。

## 错误与边界

- 审核未通过：渠道按钮可见但不可执行，明确说明前置条件。
- 渠道未配置：页面显示配置入口，不发起空任务。
- 重复点击：按钮进入稳定 loading，服务端按文章、渠道、内容版本执行幂等处理。
- 页面刷新：读取当前渠道工作流和最近一次历史，恢复到正确阶段。
- 任务失败：原文章和已成功渠道不受影响；显示失败阶段、原因、动作和重试入口。
- 文章更新：不强制重新生成 AI 建议；仅标记已有渠道产物过期。
- 旧文章已发布到 Hugo：Hugo 显示已完成，微信和小红书仍可独立开始。

## 视觉与交互约束

- 审核页发布渠道区域位于元数据和审核动作附近，不放在长页面底部。
- 渠道页面主操作区固定在首屏，任务详情和历史放在主流程之后。
- 不使用互相嵌套的卡片；渠道状态使用紧凑的列表或分段导航。
- 错误文本不能只依赖颜色，必须同时展示状态文字和处理动作。
- 桌面端使用文章内容区与工具区布局，移动端使用内容、审核、发布标签切换，禁止横向溢出。

## 非目标

- 本次不新增真正的第三方平台自动发布 API；微信和小红书仍然保持人工复制/上传确认。
- 本次不改变文章元数据、AI 建议、Hugo Provider 或小红书模板的数据格式，只调整页面边界和状态展示，必要时扩展错误响应字段。
- 本次不把三个渠道合并为“一键全平台发布”。

## 验收标准

1. 内容库进入文章后只看到审核和元数据工作，不再在侧栏底部出现 Hugo 发布流程。
2. 审核通过后，Hugo、微信、小红书三个入口同时可见且可独立进入。
3. 在任一渠道页面可以进入另外两个渠道，且不会丢失当前渠道状态。
4. 已完成、运行中、失败、过期和未配置状态都有明确文案及对应动作。
5. Hugo 失败时显示失败阶段和可执行处理建议，成功时可查看同步记录。
6. 旧文章已经同步 Hugo 时，仍可以直接进入微信或小红书，不要求重复同步 Hugo。
7. 文章更新不会自动触发 AI 重新生成；相关渠道产物只标记为需要重新处理。
8. 前端单元测试、类型检查、lint、构建和 Go 测试全部通过。
