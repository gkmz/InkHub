## 2. 产品背景

许多内容创作者使用 Obsidian 或普通 Markdown 文件长期积累知识，再将成熟文章发布到个人博客、微信公众号等渠道。写作工具解决了内容生产问题，但从“文章写完”到“各渠道正确发布”之间，仍然存在大量重复、容易出错的人工工作：

- 写作库和博客使用不同的元数据约定，标题、摘要、分类、系列、标签和 URL 需要重复维护。
- 分类和标签缺少长期治理，随着文章增加不断产生同义词、临时词和只有一篇文章的低频标签。
- 图片路径、Obsidian WikiLink、提示块和 Mermaid 等写法无法直接被所有发布渠道接受。
- 博客需要复制正文、转换图片、生成 page bundle、校验 taxonomy、构建并预览。
- 微信公众号需要将 Markdown 渲染为内联样式 HTML、处理图片，再人工粘贴到后台。
- 发布状态通常依赖记忆或简单布尔值，文章移动、改名或更新后，很难判断各渠道对应的是哪个版本。
- SEO 检查、摘要生成、关键词规划和内链建设往往发生在发布前最后一刻，质量不稳定。
- 内容处理能力分散，缺少职责清晰、可以独立扩展的标准模块。

这些问题并不只属于某一个创作者。凡是将本地 Markdown 作为长期内容源，同时经营多个发布渠道的创作者，都可能面临相同的内容治理和发布摩擦。

## 3. 问题定义

InkHub 要解决的核心问题不是“如何再写一个 Markdown 编辑器”，也不是“如何绕过平台限制实现完全自动发布”，而是：

> 如何让内容创作者只维护一份可信内容，并以简单、可靠、可检查的方式完成审核、元数据治理、SEO 优化和多渠道发布。

产品需要消除以下断点：

1. 内容源与发布副本之间缺少稳定关联。
2. 写作元数据与渠道元数据混杂或重复维护。
3. AI 可以生成标签，却缺少全库视角和确定性治理规则。
4. 发布动作分散，失败结果和渠道版本不可追踪。
5. 专业能力越来越多时，工具容易演变成复杂、臃肿的 CMS。

## 4. 产品定位

### 4.1 一句话定位

InkHub 是面向 Markdown 内容创作者的开源内容工作台，统一完成文章审核、AI 辅助元数据治理、SEO 优化和多渠道发布。

### 4.2 英文定位

> InkHub is an open-source content workspace for Markdown creators, combining editorial review, AI-assisted metadata governance, SEO optimization, and multi-channel publishing.

### 4.3 产品边界

InkHub 位于写作工具和发布平台之间：

```text
Markdown / Obsidian
        ↓
      InkHub
  审核 · 治理 · 优化 · 发布
        ↓
  Hugo · 微信公众号
```

InkHub 不替代 Obsidian，也不替代 Hugo 或微信公众号后台。它负责连接这些工具，并管理内容从“完成写作”到“完成发布”的过程。MVP 专注于这条经过真实需求验证的路径，架构通过标准 Provider 支持后续扩展。

### 4.4 品牌表达

- 产品名称统一使用 `InkHub`。
- CLI、仓库、配置键和目录名统一使用 `inkhub`。
- 中文说明使用“内容创作者的开源内容中枢”或“开源内容工作台”。
- 不使用 `Inkhub`、`Ink Hub` 等混合写法。

## 5. 产品愿景与原则

### 5.1 产品愿景

让内容创作者把精力留给思考和表达，而不是消耗在复制文件、整理标签、转换格式和确认版本上。

### 5.2 最高产品约束：简单、精美、易用

InkHub 的能力可以专业，但使用体验必须克制。产品参考微信式的极简设计理念：界面安静、层级清楚、操作直接，不用大量卡片、图表、设置项和技术术语证明功能丰富。

该原则落实为以下约束：

1. **默认路径短**：用户打开产品后，应能在少量操作内找到文章、完成审核并进入发布。
2. **一次只解决一个问题**：当前页面突出当前任务，不同时展示所有高级能力。
3. **渐进披露**：常用操作直接可见，高级设置、诊断信息和历史记录按需展开。
4. **合理默认值**：首次配置完成后，日常启动不需要指定目录或重复选择渠道。
5. **减少概念数量**：不要求普通创作者理解数据库、hash、适配器、任务队列等实现概念。
6. **避免设置泛滥**：只有存在真实用户差异且无法自动判断时才增加配置。
7. **状态可读**：使用“待审核”“博客需要更新”“微信内容已复制”等自然语言，而不是内部状态码。
8. **AI 不喧宾夺主**：AI 是助手，不使用持续弹窗、自动覆盖和夸张评分打断创作判断。
9. **视觉克制**：以内容和任务为中心，减少装饰、过度阴影、嵌套卡片和高饱和颜色。
10. **功能按需启用**：未配置 Hugo 的用户不看到 Hugo 操作，未启用 AI 的用户不承受 AI 配置负担。

### 5.3 其他产品原则

- **内容源唯一**：Markdown 文件是正文的唯一可信来源。
- **本地优先**：内容、状态和配置默认保存在用户本机。
- **人工最终确认**：AI 建议和渠道发布都允许用户检查并确认。
- **规则约束 AI**：AI 负责理解和推荐，确定性规则负责校验和治理。
- **失败可恢复**：任一渠道失败不影响其他渠道，重复执行不得制造重复内容。
- **开放可迁移**：用户可以导出配置和数据，不被数据库或专有格式锁定。
- **扩展但不臃肿**：架构允许新增内容源和发布渠道，MVP 只实现经过真实验证的能力。

## 6. 产品目标与非目标

### 6.1 产品目标

#### G1：降低日常发布成本

首次配置完成后，用户无需记忆目录和命令，即可从同一工作台完成文章审核、博客同步和微信内容准备。

#### G2：建立可信的内容状态

用户可以清楚知道文章是否审核通过、哪些渠道已处理、对应哪个正文版本，以及修改后哪些渠道需要更新。

#### G3：改善元数据长期质量

通过全库统计、Tag 使用次数、用户调整和 AI 建议，减少同义标签、一次性标签和分类漂移。

#### G4：提高发布质量

在发布前发现摘要、标题层级、图片、链接、slug、内链和渠道格式问题。

#### G5：形成可复用的开源产品

在满足真实个人工作流的基础上，允许其他 Markdown 创作者使用自己的目录、taxonomy、AI 服务和发布渠道。

### 6.2 非目标

MVP 不承担以下目标：

- 不成为新的 Markdown 编辑器。
- 不保存或托管文章正文作为云端 CMS。
- 不提供多人账号、角色权限和在线协作。
- 不追求绕过平台限制的全自动发布。
- 不自动重写正文或未经确认覆盖元数据。
- 不首期支持所有内容平台。
- 不建设插件市场和复杂扩展运行时。
- 不提供流量分析、广告投放或商业化运营套件。
- 不以大量 AI 生成功能代替创作者判断。

## 7. 目标用户

### 7.1 核心用户

#### Markdown 多渠道创作者

特征：

- 使用 Obsidian、Typora、VS Code 等工具写作。
- 使用 Git 管理或备份内容。
- 同时维护个人博客和一个或多个内容平台。
- 对内容所有权、格式质量和长期可维护性有要求。
- 愿意使用本地工具，但不希望每次发布都操作脚本。

核心诉求：维护一份内容，稳定发布到多个渠道。

### 7.2 次要用户

#### 独立开发者与技术博主

重视代码块、Mermaid、图片路径、Hugo taxonomy、SEO 和 Git 工作流。

#### 知识型内容创作者

拥有长期积累的主题、系列和标签，希望 AI 提高整理效率，但不希望知识结构被 AI 随意改变。

#### 开源贡献者

希望新增 Source Provider、Publish Provider、AI Provider、检查规则或微信公众号模板，并需要清晰稳定的扩展边界。

### 7.3 暂不服务的用户

- 只在单个平台原生编辑器中写作的用户。
- 需要多人协同、审批权限和企业合规审计的团队。
- 希望自动批量生成和自动群发营销内容的用户。
- 完全不接触本地文件系统且只使用移动设备的用户。

## 8. 典型使用场景

### 8.1 首次建立工作区

用户首次启动 InkHub，选择自己的 Obsidian Vault。InkHub 自动识别附件设置、Hugo 项目和 taxonomy 文件，用户确认后保存。以后直接运行 `inkhub` 即可进入上次工作区。

### 8.2 审核一篇候选文章

用户在 Obsidian 完成文章，打开 InkHub。工作台显示该文章缺少摘要、分类和 tags。用户运行 AI 建议，接受部分结果，完成必要检查并标记“审核通过”。

### 8.3 发布到 Hugo 博客

用户点击“同步到博客”。InkHub 显示目标路径和将发生的变化，随后复制图片、转换内容、校验 taxonomy、执行 Hugo build，并提供本地预览入口。

### 8.4 准备微信公众号内容

用户点击“准备微信内容”。InkHub 处理本地图片、Mermaid 和内联样式，展示最终效果。用户复制格式化内容，粘贴到微信后台并返回确认“已保存草稿”。

### 8.5 更新已发布文章

用户修改了 Markdown 正文。InkHub 根据内容 hash 将博客和微信状态标记为“内容已更新”，并明确显示需要重新处理的渠道。

### 8.6 治理长期标签

用户查看 tag 治理页面，发现多个同义 tag 和低频 tag。InkHub 推荐合并关系并展示受影响文章，用户确认后执行批量治理。

## 9. 核心概念

### 9.1 工作区 Workspace

一组相互关联的内容源、元数据规则、AI 设置和发布渠道配置。一个用户可以创建多个工作区，但日常默认进入最近使用的工作区。

### 9.2 内容源 Content Source

保存 Markdown 正文的来源。MVP 只提供 Obsidian Source Provider。

### 9.3 文章 Article

InkHub 从内容源识别出的可管理 Markdown 文件。文章正文不存入数据库，数据库只保存索引、状态和可重建信息。

### 9.4 稳定文章 ID

文章不因移动目录、修改文件名或调整标题而改变的身份标识。MVP 统一将稳定 ID 写入 Obsidian Markdown 的 frontmatter，不支持 sidecar 或仅数据库身份模式。

### 9.5 Taxonomy

内容分类体系，包括 category、series、tag、alias 和治理规则。

### 9.6 Provider

Provider 是 InkHub 的标准能力扩展边界，分为四类：

- **Source Provider**：读取内容源并将其转换成 InkHub 标准文章模型。
- **AI Provider**：提供摘要、标签、SEO 等智能分析能力。
- **Publish Provider**：将标准文章模型转换并交付到目标渠道。
- **Taxonomy Provider**：发现并受控修改发布平台的标准分类体系。

MVP 内建 Obsidian Source Provider、OpenAI-compatible AI Provider、Hugo Publish Provider 和 WeChat Publish Provider。Provider 是内部标准模块，不等同于外部脚本或松散的命令调用。

### 9.7 内容版本

根据规范化正文计算的 hash，用于判断已审核或已发布内容是否仍与当前文件一致。

## 10. 整体工作流

### 10.1 首次使用

```text
启动 InkHub
  → 创建工作区
  → 选择 Obsidian Vault
  → 自动检测资源与集成
  → 确认 InkHub frontmatter 规则
  → 可选配置 AI
  → 添加发布渠道
  → 扫描内容
  → 进入工作台
```

### 10.2 日常发布

```text
在原写作工具完成文章
  → InkHub 自动发现更新
  → 补齐或确认元数据
  → 执行内容与 SEO 检查
  → 审核通过
  → 选择发布渠道
  → 预览渠道结果
  → 发布或复制
  → 确认渠道结果
```

### 10.3 核心状态

用户界面使用以下自然语言状态：

- 草稿
- 待补充信息
- 待审核
- 审核通过
- 准备中
- 可以发布
- 已发布或已处理
- 内容已更新
- 处理失败

内部允许使用更细状态，但不得直接暴露给普通用户。

## 11. 信息架构

MVP 主导航保持精简：

1. **工作台**：待办、最近文章和发布状态。
2. **内容库**：查找、筛选和查看全部文章。
3. **标签治理**：查看分类体系和治理问题。
4. **设置**：工作区、AI、发布渠道和诊断。

文章审核、SEO、AI 建议、发布历史等能力进入文章详情，不增加同级主导航。

### 11.1 工作台

工作台只展示明确标记为“已就绪”的内容，并回答“现在应该做什么”：

- 处理失败。
- 内容已更新，需要重新审核。
- 等待审核。
- 审核通过，等待渠道交付。
- 最近修改的 10 篇已就绪文章。
- 最近处理记录。

工作台分组由后端按优先级互斥计算，每篇文章只显示一个主要动作。没有已就绪文章时，说明在 frontmatter 设置 `publish.status: ready`，并引导进入内容库。

不默认展示访问量图表、全库统计大屏或装饰性数据卡片。

### 11.2 内容库

内容库支持：

- 按标题搜索。
- 按目录、分类、系列、tag 和状态筛选。
- 查看最后修改时间和渠道状态。
- 按“全部、已就绪、草稿”组织全部文章；缺少或非法的 `publish.status` 均按草稿处理并保留修复提示。
- 快速进入文章详情。

默认视图应适合扫描大量文章，避免每篇文章使用尺寸过大的卡片。

### 11.3 文章详情

文章详情采用“内容预览为主、审核工具为辅”的结构，包含：

- 文章预览。
- 当前元数据。
- 检查结果。
- AI 建议。
- 发布渠道和状态。
- 按需展开的历史记录。

同一时间只突出一个主要操作，例如“补充信息”“审核通过”或“同步到博客”。

### 11.4 关键交互验收

- 首次初始化最多包含 4 个连续步骤：选择 Vault、确认 Hugo 与 taxonomy、配置微信模板、可选配置 AI。
- 每一步只展示当前必需字段，自动检测成功的字段默认收起。
- 日常从工作台打开一篇元数据完整的文章，到完成审核不超过 3 次主要操作。
- 审核完成页连续展示“同步到 Hugo”和“准备微信内容”，用户不需要返回内容库。
- AI 建议位于文章元数据编辑区域内，由用户主动触发，不使用全局弹窗。
- 微信模板在 Provider 设置中选择工作区默认值；文章发布时可以临时切换，但不修改默认值。
- 默认界面不展示 Provider、content hash、任务队列和数据库等内部术语。

## 12. 工作区与配置

### 12.1 初始化向导

首次运行且不存在工作区时，InkHub 自动打开初始化向导。

必填步骤：

1. 输入工作区名称。
2. 选择 Obsidian Vault 根目录。
3. 确认扫描结果。

可选步骤：

- 配置 Hugo。
- 选择微信公众号模板并配置图片托管。
- 配置 AI Provider。
- 确认 Hugo taxonomy 文件。

可选步骤允许跳过，避免首次使用被复杂配置阻塞。

### 12.2 自动检测

选择 Obsidian Vault 后，InkHub 首先校验 `.obsidian` 目录，再尝试检测：

- Obsidian `.obsidian` 目录和附件设置。
- 常见 `assets` 或附件目录。
- 同级或配置路径中的 Hugo 项目。
- Hugo `hugo.yaml`、`hugo.toml`。
- taxonomy 配置。
- Git 仓库。
- InkHub 工作区配置。

自动检测结果必须允许用户修改。

### 12.3 配置优先级

配置按以下优先级生效：

```text
命令行参数
  → 环境变量
  → 工作区 .inkhub/config.yaml
  → 本机 SQLite 设置
  → 应用默认值
```

- 可共享规则写入 `.inkhub/config.yaml`。
- 本机绝对路径和界面偏好存入 SQLite。
- API Key、Token 等 Secret 存入操作系统 Keychain或环境变量。

### 12.4 启动体验

首次配置后，用户直接运行：

```bash
inkhub
```

InkHub 使用最近工作区并打开本地工作台。仍保留高级命令：

```bash
inkhub --workspace personal
inkhub --dir /temporary/notes
inkhub doctor
inkhub scan
inkhub db backup
```

`--dir` 仅临时覆盖，不自动改变已保存工作区。

## 13. 内容扫描与文章身份

### 13.1 扫描范围

Obsidian Source Provider 扫描 `.md` 文件，并允许配置排除规则，例如：

- `.git`
- `.obsidian`
- `_Index.md`
- `_MOC.md`
- 模板目录
- 归档或私密目录

MVP 不支持 AsciiDoc 或其他内容格式。后续由新的 Source Provider 扩展，不在 Obsidian Provider 中累积兼容逻辑。

### 13.2 增量索引

- 首次建立工作区时执行全量扫描。
- 后续启动执行增量扫描。
- 运行期间监听新增、修改、移动和删除。
- 文件删除后保留历史发布记录，文章索引进入软删除状态。
- 扫描失败不阻止查看其他已索引文章。

### 13.3 稳定 ID

MVP 将稳定 ID 写入文章 frontmatter。该方案可以跟随文章移动和 Git 同步，且不会让数据库成为文章身份的唯一来源。

- 首次进入发布流程时，InkHub 自动生成 ID 并在写入前提示用户。
- 已存在 ID 时保持不变。
- 重复 ID 阻止审核和发布。
- 后续 Source Provider 可以在不改变内部文章模型的前提下实现自己的身份持久化方式。

### 13.4 Frontmatter 标准与 Provider 映射

InkHub Core 使用统一文章模型。MVP 的 Obsidian Source Provider 按以下固定标准读取和写回 frontmatter，不提供自定义字段映射，避免首次版本引入双向映射歧义：

```yaml
---
id: article_01J2ABCDEF
title: 示例标题
description: 文章概要
tags:
  - go
  - 流式输出
keywords:
  - Go 流式输出
  - Markdown 发布
publish:
  category: AI应用开发
  series: 大模型应用开发入门
  slug: llm-streaming-guide
  cover: assets/cover.png
---
```

字段契约如下：

- `id`、`title`、`description`、`publish.category`、`publish.series`、`publish.slug` 和 `publish.cover` 为字符串。
- `tags` 和 `keywords` 为字符串数组。
- `publish.series` 和 `publish.cover` 可为空或省略。
- Category 在 MVP 中只允许一个；Series 最多一个。
- 审核状态、渠道状态、content hash 和发布时间只保存在 SQLite，不写入源文章。
- Provider 读取源字段后转换成 Core 标准模型；写回时执行相反转换。
- MVP 不识别 `summary`、`excerpt`、`serials` 等替代字段，也不自动迁移历史字段。
- 写回单个字段时保留正文和无关 frontmatter 字段的原始顺序与内容。

后续 Source Provider 可以声明自己的字段映射，但不能改变 Core 标准模型。

## 14. 元数据设计

### 14.1 内部标准字段

| 字段 | 用途 | 是否必需 |
| --- | --- | --- |
| ID | 稳定关联文章、状态和渠道副本 | 发布前必需 |
| Title | 展示和发布标题 | 必需 |
| Description | 摘要、搜索和社交分享描述 | 发布前必需 |
| Category | 单个主导航分类 | 博客发布前必需 |
| Series | 连续栏目或课程 | 可选 |
| Tags | 跨分类主题与概念 | 发布前必需 |
| Slug | 稳定 URL | 博客发布前必需 |
| Cover | 社交分享或渠道封面 | 可选或按渠道要求 |
| Keywords | SEO 补充关键词 | 可选 |

### 14.2 写作元数据与发布元数据

InkHub 的标准文章模型与具体文件格式分离。MVP 的 Obsidian Source Provider 必须使用 13.4 节定义的 frontmatter，不再提供第二套结构。

Publish Provider 负责将标准文章模型转换成渠道所需格式，不要求源文章采用 Hugo frontmatter。

## 15. 审核工作流

### 15.1 审核条件

文章可以标记“审核通过”前，必须满足：

- 标题存在。
- 稳定 ID 存在。
- 必填元数据已补齐。
- Markdown 和 frontmatter 可解析。
- 本地图片可访问。
- 不存在阻断级内容检查问题。
- AI 建议无需全部接受。

渠道特有问题在选择对应渠道后检查，不阻止其他渠道。

### 15.2 审核失效

正文或影响发布的元数据变化后：

- 当前审核状态变为“内容已更新，需要确认”。
- 已处理渠道根据各自 content hash 标记为过期。
- 纯内部字段或不影响输出的设置变化不应使审核失效。

### 15.3 修改原则

- AI 和规则检查默认只提出建议。
- 写回 Markdown 前展示字段级差异。
- 用户可以逐项接受或拒绝。
- 写回采用原子操作。
- 不因修改一个字段而格式化整篇文章。

## 16. Taxonomy 与 Tag 治理

### 16.1 治理目标

- Category 保持少量、稳定，负责主导航。
- Series 只表示连续内容，不成为第二套 tags。
- Tags 描述跨分类主题，但避免同义漂移和一次性滥用。
- 允许必要的低频产品名、专有技术名和新主题。

### 16.2 Taxonomy 来源

MVP 只支持发布平台权威模式：Hugo 配置中的 `taxonomies`、文章 frontmatter 和 taxonomy term 页面共同构成权威来源。SQLite 持久化最近成功快照、同步状态和使用统计，但不取代 Hugo 标准资源。

- InkHub 首次关联 Hugo 时完成全量发现，后续通过 revision 和文件变化增量刷新。
- AI 和人工新增 term 必须经过准入确认后，由 Taxonomy Provider 生成并应用 Hugo 原生资源变更。
- 写回前展示 Provider 原生变更，并校验期望 revision、格式和规则。
- 写回失败时不更新数据库缓存，也不修改文章。
- Hugo Provider 未配置或标准 taxonomy 资源不可解析时，允许浏览和微信发布；界面继续展示最近成功缓存，并禁用 taxonomy 修改与 Hugo 发布。
- InkHub 自主管理 taxonomy 和跨 Provider 合并 taxonomy 均属于 Release 1 之后的能力。

### 16.3 Tag 索引

InkHub 统计：

- 规范化后的 tag 名称。
- 使用次数。
- 对应文章。
- 所属 category 和 series 分布。
- 最近使用时间。
- 标准显示名称和来源标识。

### 16.4 推荐规则

每篇文章默认建议 3 至 6 个 tags：

- 1 个技术栈或大主题。
- 1 至 3 个核心概念。
- 0 至 1 个工程场景。
- 0 至 1 个产品或专有名词。

确定性规则包括：

- 优先选择现有 tag。
- 命中已有 tag 时使用快照中的标准显示名称。
- category 和 series 不机械重复为 tag。
- 超出推荐数量时提示用户调整，但不阻止保存。
- 新 tag 允许直接加入文章，并在发布和下次 taxonomy 刷新后自然入库。

### 16.5 Tag 调整

文章编辑器展示：

- 已有 tag 及其文章使用数量。
- 当前文章已经选择的 tags。
- AI 生成的 tag 候选和简短理由。
- AI 候选是否来自现有 taxonomy。

用户可以：

- 搜索并选择现有 tag。
- 直接创建新 tag。
- 逐项采用或忽略 AI 建议。
- 删除或调整当前文章的 tags。

AI 默认优先推荐复用现有 tag，但不替代用户决策。未配置 AI 时，完整的手工编辑能力仍然可用。

### 16.6 治理页面

治理页面只突出需要处理的问题：

- 同义或近义 tag。
- 未知 category 或 series。
- 低频 tag。
- 超过推荐数量的文章。
- 无 tag 文章。

批量修改前必须展示受影响文章和变更预览。

## 17. AI 元数据助手

### 17.1 能力范围

MVP 支持 AI 建议：

- 文章摘要。
- Category。
- Series。
- Tags。
- SEO 标题建议。
- Slug。
- 主关键词与次关键词。
- 图片 alt 文本。

AI 不自动发布，不未经确认修改正文，不擅自创建 taxonomy。

### 17.2 Provider 支持

MVP 支持 OpenAI-compatible API，并允许配置：

- Provider 名称。
- Base URL。
- API Key。
- 模型名称。
- 超时。
- 最大输入长度。
- 是否允许发送完整正文。

该方式可兼容 OpenAI、DeepSeek、Ollama 和其他兼容服务。后续可增加原生 Provider 适配。

### 17.3 AI 推荐流程

```text
本地提取文章结构与关键词
  → 从现有 taxonomy 召回候选
  → 将候选、统计和文章内容提供给 AI
  → AI 返回结构化建议
  → 规则引擎校验
  → 用户逐项确认
  → 写回文章 frontmatter
```

这种方式避免 AI 在没有全库上下文时自由创造大量 tags。

### 17.4 结构化输出

AI 必须返回可校验的结构化结果，至少包含：

```json
{
  "description": "",
  "category": "",
  "series": "",
  "recommended_tags": [],
  "new_tag_candidates": [],
  "slug": "",
  "primary_keyword": "",
  "secondary_keywords": [],
  "reasons": {}
}
```

无效 JSON、未知 taxonomy、超出数量限制或重复 slug 不得直接进入文章。

### 17.5 交互原则

- 用户主动触发 AI 分析。
- 建议中心按 Description、Category、Series、Slug、Keywords 和 Tags 分组展示建议值与理由。
- 每项可以单独采用或忽略；每个字段组支持批量采用和批量忽略。
- 采用建议只进入文章编辑草稿，必须由用户点击 `保存到文章` 才写回 Markdown。
- 展示简短推荐原因，避免建议项被长解释挤压。
- AI 失败时显示可理解的原因，不阻塞手工审核。
- 每次生成创建独立建议版本；重复生成不会覆盖旧版本，建议历史可按文章查询并只读查看。
- 建议对应旧内容版本时标记为过期并禁用采用；重新生成后才可继续处理。

### 17.6 隐私

- 调用前明确当前 Provider 是否为本地服务。
- 用户可以选择只发送标题和摘要、发送结构化摘录或发送全文。
- 日志不记录 API Key 和完整正文。
- AI 功能可完全关闭。
- Secret 优先存入操作系统 Keychain。

## 18. SEO 与内容质量检查

### 18.1 设计原则

InkHub 不承诺通过一个分数决定 SEO 好坏。检查结果分为：

- **必须修复**：会导致发布失败或页面明显错误。
- **建议修复**：可能影响可读性、索引或分享效果。
- **可选优化**：由创作者结合表达目标判断。
- **已通过**：无需处理。

### 18.2 通用检查

- 标题是否缺失、过长或与正文不符。
- Description 是否缺失、过短、过长或与标题机械重复。
- 是否只有一个 H1。
- H2/H3 层级是否跳跃。
- 图片是否缺失或缺少 alt。
- 图片尺寸是否明显过大。
- 本地链接和图片引用是否可解析。
- 代码块是否声明语言。
- Slug 是否稳定、合法和唯一。
- 是否存在明显孤立文章。
- 是否有适合的相关文章内链。

### 18.3 Publish Provider 检查

Hugo Publish Provider 负责检查：

- Canonical。
- Open Graph。
- Twitter Card。
- Article Schema JSON-LD。
- Sitemap 和 robots。
- 封面图。
- 构建后的 description、日期和关键词输出。

微信公众号 Publish Provider 负责检查：

- 标题和摘要长度提示。
- 图片是否能被微信后台访问。
- 内联样式是否完整。
- 不支持的 HTML 或 Markdown 结构。
- Mermaid 是否已转换。

### 18.4 内链建议（Release 1 之后）

InkHub 基于历史文章标题、摘要和 tags 推荐 3 至 5 篇相关文章，并提供：

- 推荐文章。
- 推荐原因。
- 建议锚文本。
- 建议插入位置。

用户确认后才修改正文。该能力不进入 MVP Release 1，也不自动反向修改旧文章。

## 19. Provider 设计

### 19.1 标准职责

四类 Provider 都必须遵循小而稳定的职责边界：

- Source Provider 只负责发现、读取、监听和写回源内容。
- AI Provider 只负责执行结构化智能任务，不管理文章状态。
- Publish Provider 只负责渠道预检、转换、预览和交付，不直接修改源文章。
- 审核状态、任务编排、数据库和用户确认由 InkHub Core 管理。

Provider 以 Go 接口和标准数据结构集成到 InkHub 内部。MVP 不通过外部脚本拼装核心流程，也不把某个渠道的规则写入 Core。

### 19.2 Publish Provider 通用能力

每个 Publish Provider 声明自身支持的能力：

- 预检。
- 准备内容。
- 本地预览。
- 创建草稿。
- 直接发布。
- 图片处理。
- Taxonomy。
- Canonical。
- 是否需要人工确认。

界面只展示该实例支持的操作。

### 19.3 Publish Provider 实例

MVP 每个工作区只允许一个 Hugo Publish Provider 实例和一个 WeChat Publish Provider 实例。实例独立保存非敏感配置、Secret 引用和发布状态。

数据模型必须包含稳定的 Provider 实例 ID，为 Release 1 之后的同类型多实例预留能力，但 MVP 界面不提供添加第二个同类型实例的入口。

### 19.4 发布原则

- 不提供含义模糊的“一键全平台发布”。
- 用户可以选择一个或多个渠道依次处理。
- 单个渠道失败不回滚已经成功的其他渠道。
- 重复操作必须幂等或明确提示将覆盖什么。
- 渠道结果与具体内容 hash 关联。

## 20. Hugo Publish Provider

### 20.1 MVP 能力

- 读取 Hugo 根目录和默认 section 配置。
- 将 Obsidian Markdown 转换为 Hugo page bundle。
- 复制文章引用的本地图片。
- 重写图片路径。
- 转换 Obsidian WikiLink、提示块等不兼容写法。
- 从统一元数据生成 Hugo frontmatter。
- 写入 `source_id` 和可选 `source_path`。
- 根据 `source_id` 更新已有 bundle。
- 执行 taxonomy 校验。
- 执行 Hugo build。
- 提供本地预览入口。
- 记录目标路径、URL、content hash 和结果。

### 20.2 同步流程

```text
渠道预检
  → 确定目标 bundle
  → 展示变更摘要
  → 转换正文与资源
  → 创建包含目标变更的临时站点
  → 在临时站点执行 Taxonomy 校验与 Hugo build
  → 原子替换目标 bundle
  → 在真实站点执行快速构建确认
  → 提供预览
```

如果临时校验、构建、替换或最终确认任一步失败，InkHub 必须恢复原目标 bundle，不得标记同步成功。重复同步同一 `source_id` 必须更新同一 bundle，不产生重复页面。

### 20.3 内部集成要求

Hugo 内容转换、page bundle 生成、图片复制、路径重写、taxonomy 校验和构建编排必须作为 InkHub 内部能力实现，不依赖外部导入脚本。

- 内容转换逻辑位于 Hugo Publish Provider。
- 通用 Markdown 和资源处理能力位于可复用的内部服务。
- Hugo CLI 仍可作为官方构建工具调用，但调用由 Provider 管理，并通过结构化结果返回给 Core。
- Provider 的单元测试不依赖维护者个人博客和绝对路径。
- 原项目脚本只作为需求和行为参考，不成为 InkHub 的运行依赖。

### 20.4 不包含的能力

- 默认不自动 Git commit。
- 默认不自动 push。
- 默认不自动部署生产环境。
- 后续可以作为明确、独立且可确认的动作增加。

## 21. 微信公众号 Publish Provider 与模板系统

### 21.1 MVP 能力

- 使用符合 InkHub 模板标准的微信公众号模板渲染 Markdown。
- 代码高亮使用内联样式。
- 处理本地图片并上传到已配置的公开图床。
- 转换 Mermaid 为图片。
- 处理 Obsidian 图片语法。
- 生成最终 HTML。
- 在 InkHub 内预览最终效果。
- 复制格式化内容到剪贴板。
- 快捷打开微信公众平台。
- 用户手动确认“已保存草稿”。

### 21.2 模板标准

InkHub 定义独立于单篇文章和用户工作区的微信公众号模板标准。模板必须可以创建、安装、预览、导出和分享。

每个模板包至少包含：

```text
template-id/
├── template.yaml
├── styles.css
├── preview.md
├── preview.png
└── assets/
```

`template.yaml` 至少声明：

- 标准版本。
- 唯一模板 ID。
- 名称与简介。
- 作者和许可证。
- 模板版本。
- 支持的 InkHub 版本范围。
- 模板 target、入口格式、Renderer 和兼容 Provider。
- 入口样式文件。
- 可配置变量。
- 依赖的字体或资源。
- 支持的 Markdown 元素。

模板样式需要覆盖正文、标题、引用、列表、表格、链接、图片、代码、提示块、分隔线和脚注等标准内容元素。InkHub 负责将模板 CSS 转换成微信公众号可粘贴的内联样式，模板作者不需要自行实现复制逻辑。

模板标准使用独立语义版本，例如 `specVersion: 1.1`。模板自身使用 `version` 字段遵循语义化版本：

- 模板修复样式但不改变变量契约时递增 patch。
- 新增向后兼容变量或元素样式时递增 minor。
- 删除变量或产生明显不兼容视觉变化时递增 major。
- InkHub 只安装其支持的标准版本和兼容范围。

### 21.3 模板变量

模板变量只允许 `color`、`font-family`、`font-size`、`spacing`、`enum` 和 `boolean` 六种类型，并必须声明默认值、可选值或最小/最大边界。模板可以声明少量受控变量，例如：

- 主色。
- 字号档位。
- 正文字体族。
- 代码主题。
- 段落间距。
- 是否显示文末品牌信息。

模板不得通过无限配置项演变成页面设计器。变量必须有默认值，并在标准预览内容中验证。

### 21.4 模板安全边界

- 模板只能包含声明文件、CSS、标准预览 Markdown、预览图和静态资源。
- 禁止 JavaScript、可执行文件、动态模板表达式和任意本地文件引用。
- CSS 禁止 `@import`、`behavior`、脚本 URL 和未声明的远程资源。
- CSS 属性使用 InkHub 维护的允许列表；未知或不适用于微信公众号的属性在校验时失败。
- 模板规范 1.x 只允许安全字体 token，由 InkHub 映射为跨平台字体栈；不携带或下载远程字体文件。
- 模板包内路径不得逃逸模板根目录。
- 安装时校验文件清单、内容 SHA-256 和模板索引记录。
- 模板更新失败或新版本校验失败时继续使用上一个可用版本。

### 21.5 模板创建与发布

模板作者可以：

1. 使用 `inkhub template init` 创建标准模板。
2. 在本地预览标准 Markdown 测试稿。
3. 运行 `inkhub template validate` 校验结构、安全和元素覆盖。
4. 导出模板包。
5. 将模板发布到 InkHub 模板仓库。

其他用户可以在 InkHub 中浏览、预览、安装、更新和停用模板。MVP 使用由 InkHub 项目维护的公开 Git 仓库作为模板索引和分发源；模板作者通过 Pull Request 提交模板包和清单，不建设复杂的商业模板市场和账号系统。

模板仓库提供版本化 `index.json`，每个条目至少包含模板 ID、名称、作者、版本、标准版本、下载地址、包 SHA-256、预览图、许可证和兼容 InkHub 版本。InkHub 下载索引失败时仍可使用已安装模板。

模板发布要求：

- 使用明确的开源或分发许可证。
- 不包含远程执行代码。
- 不读取文章之外的本地数据。
- 外部资源必须声明来源和许可。
- 通过标准预览和复制结果检查。
- 相同模板版本内容不可变。

### 21.6 内置默认模板

现有微信公众号样式改造为首个符合标准的内置模板，而不是保留在 WeChat Provider 的硬编码 CSS 中。

- 模板暂定名称：`InkHub Default`。
- 与第三方模板使用相同目录结构、清单和校验规则。
- 用户可以复制该模板作为自定义模板起点。
- InkHub 在没有安装其他模板时默认使用它。
- `InkHub Default` 同时作为模板标准的参考实现和公开仓库中的首个模板。
- MVP 提供第二个测试模板 `InkHub Minimal`，用于验收第三方模板同等的安装、切换和渲染链路。

### 21.7 状态语义

- “内容已准备”：转换与图片处理成功。
- “已复制”：当前 content hash 的 HTML 已复制。
- “草稿已确认”：用户确认已经粘贴并保存到微信后台。
- “内容已更新”：源文章发生变化，微信草稿可能不是当前版本。

InkHub 不将“复制成功”误认为“发布成功”。

### 21.8 边界

由于个人公众号发布接口不可用或受限，MVP 不依赖官方草稿 API，也不以易失效的 DOM 自动化作为核心流程。

## 22. 设置与诊断

### 22.1 设置分组

设置页面只保留四组：

1. 工作区。
2. AI。
3. 发布渠道。
4. 数据与诊断。

每组默认展示最常用设置，高级项折叠。

### 22.2 工作区设置

- 工作区名称。
- Obsidian Vault 目录。
- 自动识别的附件目录。
- 排除规则。
- Hugo taxonomy 文件路径。
- 默认微信公众号模板。

### 22.3 AI 设置

- Provider。
- Base URL。
- 模型。
- Secret 状态。
- 隐私模式。
- 测试连接。

### 22.4 发布渠道设置

- 已启用 Publish Provider 实例。
- 添加、测试、停用和删除实例。
- 渠道特有配置。
- Secret 状态。
- 微信公众号模板浏览、安装、更新和默认模板选择。

### 22.5 Doctor

`inkhub doctor` 和设置页诊断功能检查：

- 内容目录是否存在且可读。
- 配置和数据库是否可写。
- Taxonomy 是否可解析。
- AI Provider 是否可连接。
- Hugo 命令和项目是否有效。
- Hugo CLI 是否可用。
- 已安装微信公众号模板是否通过标准校验。
- 图片上传配置是否完整。
- 本地端口是否可用。

诊断结果使用“正常、需要处理、未启用”三类表达，避免堆叠技术日志。

## 23. 数据存储

### 23.1 存储原则

- Markdown 正文始终保存在内容源。
- SQLite 保存应用状态、索引、配置和历史。
- Taxonomy 根据工作区模式保存在 InkHub 配置或外部文件。
- Secret 不以明文保存到普通数据库。
- 可重建的数据与不可丢失的数据明确区分。

### 23.2 SQLite 选择

InkHub 使用 SQLite，原因包括：

- 本地单机无需独立数据库服务。
- 支持事务、约束、迁移和可靠并发控制。
- 适合发布历史、AI 建议、工作区和任务状态。
- 单文件易于备份。
- 可以保持单机工具的简单部署体验。

Go 实现优先使用不依赖 CGO 的 SQLite 驱动，保证跨平台单文件分发。

### 23.3 核心实体

- `workspaces`：工作区。
- `sources`：内容源。
- `articles`：文章索引。
- `taxonomy_terms`：Taxonomy 缓存与统计。
- `article_taxonomies`：文章分类关系。
- `provider_instances`：Provider 实例。
- `publications`：渠道处理记录。
- `publication_events`：状态事件。
- `ai_suggestions`：AI 建议与采用情况。
- `templates`：模板安装、版本和来源信息。
- `jobs`：后台任务。
- `settings`：非敏感设置。

具体字段和索引在技术设计中定义，PRD 要求所有关键状态可追踪、迁移和恢复。

### 23.4 数据目录

应用遵循操作系统数据目录规范。macOS 默认使用：

```text
~/Library/Application Support/InkHub/
```

其中包括：

- `inkhub.db`
- 日志。
- 自动备份。
- 临时任务文件。

允许通过 `--data-dir` 覆盖。

### 23.5 备份与恢复

- 数据库迁移前自动备份。
- 每日首次重要写入时生成轮换备份。
- 默认保留最近 7 至 14 份。
- 支持手工备份和恢复。
- 支持从内容源重新构建文章与 taxonomy 索引。
- 发布历史和人工确认记录作为不可重建数据重点保护。

## 24. 全新产品与数据导入边界

### 24.1 全新产品原则

InkHub 按新的标准文章模型、Provider 接口和 SQLite 状态模型设计，不以兼容原 `markdown-preview` 的代码结构、JSON 数据或外部脚本为产品约束。

- 旧代码可以作为已经验证的用户需求和渲染效果参考。
- 新实现按 InkHub 的职责边界重新组织。
- MVP 不提供旧 JSON 发布状态自动迁移。
- MVP 不承诺复用旧路径 ID 或旧平台配置。
- 用户首次使用 InkHub 时创建新工作区并重新建立索引。

### 24.2 内容导入

不兼容旧系统不等于复制或破坏已有文章。Obsidian Source Provider 直接读取现有 Vault，并按 InkHub 标准逐步补充稳定 ID 和发布元数据。已有 Hugo 内容保持不变，只有用户主动同步的文章才进入 InkHub 管理关系。

### 24.3 数据写入安全

- 首次批量写入稳定 ID 前展示影响文章数量。
- 所有 Markdown 写入使用原子替换。
- InkHub 不自动删除旧 JSON、脚本或 Hugo 内容。
- 新数据库迁移前自动备份，迁移只针对 InkHub 自身 schema。

## 25. 后台任务

MVP 使用本地持久化任务队列处理耗时操作：

- 扫描工作区。
- 分析文章。
- 刷新 taxonomy。
- 同步 Hugo。
- 构建 Hugo。
- 准备微信内容。

产品要求：

- 用户能看到当前任务和进度。
- 页面刷新后任务状态不丢失。
- 同一文章不能同时执行冲突任务。
- 任务失败后提供重试。
- 退出应用时不制造半写入文件。
- 日常页面不默认展示完整任务队列，只有运行或失败时出现状态。

## 26. 安全与隐私

- Web 服务默认只监听 `127.0.0.1`。
- 文件访问限制在已配置的内容源、资源目录和发布目标中。
- 外部命令不拼接未经校验的 shell 字符串。
- 文件写入使用临时文件和原子替换。
- API Key、GitHub Token 等 Secret 不写入日志、普通数据库或 Git 配置。
- AI 请求明确数据发送范围。
- 诊断包默认不包含正文和 Secret。
- 图片上传前列出即将上传的文件。
- Provider 只能操作其配置允许的目录和能力范围。
- 所有破坏性批量操作提供影响预览和确认。

## 27. 异常与边界处理

### 27.1 内容异常

- Frontmatter 解析失败：展示具体位置，不阻止查看正文。
- 重复稳定 ID：阻止发布，并引导重新分配其中一个 ID。
- 图片丢失：标记阻断对应渠道，不影响其他文章。
- 文件移动：使用稳定 ID 维持历史关联。
- 文件删除：保留发布历史，允许确认清理索引。

### 27.2 AI 异常

- 超时：允许重试或继续手工处理。
- 无效结构化输出：不写入文章，展示简洁错误。
- 未知 tag：进入新 tag 候选，不自动采用。
- 服务不可用：隐藏或禁用 AI 操作，其他流程正常。

### 27.3 Publish Provider 异常

- Hugo 校验失败：不标记同步成功。
- Hugo build 失败：保留错误摘要和日志入口。
- 图片上传部分失败：不复制不完整的微信发布内容。
- 剪贴板失败：允许下载或查看最终 HTML 作为兜底。
- 一个渠道失败：其他渠道状态保持不变。

## 28. 开源与扩展策略

### 28.1 开源目标

- 让其他 Markdown 创作者可以独立安装和使用。

- 提供可理解的模块边界，方便贡献 Provider、模板和检查规则。
- 核心功能不依赖私有云服务。

### 28.2 扩展边界

产品内部按以下边界组织：

- Source Provider。
- InkHub Core 与 Metadata Store。
- Taxonomy Rules。
- AI Provider。
- Content Checker。
- Publish Provider。
- WeChat Template。

MVP 使用编译期内置 Provider，不建设动态插件市场。Provider 标准先保证内部职责分离和可测试性，只有当第三方集成数量和独立发布需求得到验证后，再评估进程外插件协议。微信公众号模板从 MVP 起使用公开标准，因为模板本身是无执行代码的内容包，适合独立分享。

## 31. 成功指标

MVP 阶段优先衡量工作流效果，不追求虚荣指标。

### 31.1 效率指标

- 首次配置后，日常启动不需要再次指定内容目录。
- 一篇元数据基本完整的文章可以在一个工作台中完成博客和微信准备。
- Hugo 同步不再需要手工复制正文与图片。
- 用户能在 10 秒内判断一篇文章哪些渠道需要更新。

### 31.2 质量指标

- 稳定 ID 覆盖所有进入发布流程的文章。
- 发布状态与内容 hash 关联，不因移动文件丢失。
- AI 推荐的新 tag 不会未经确认进入 taxonomy。
- Category、series 和 tag 数量限制在发布前得到校验。
- Hugo build 和渠道阻断问题不会被标记为成功。

### 31.3 易用性指标

- 新用户无需阅读完整文档即可完成工作区创建。
- 未配置的功能不占据主要界面。
- 日常主流程不要求理解内部技术概念。
- 常用操作在文章详情中有明确唯一的主要按钮。

### 31.4 开源指标

- 可以通过文档在新环境完成安装和首次工作区创建。
- 核心功能不依赖维护者个人路径、脚本和仓库。
- 新增 Provider 不需要修改无关 Provider 和核心状态逻辑。
- 第三方微信模板可以使用标准工具完成校验和安装。

## 32. MVP 验收标准

### 32.1 工作区

- 首次启动可以选择并校验 Obsidian Vault，随后保存工作区。
- 再次启动自动进入最近工作区。
- 路径失效时给出修复入口，不崩溃。
- 可以临时使用 `--dir` 覆盖。

### 32.2 内容库

- 可以扫描、搜索和筛选文章。
- 文件修改后索引和 hash 正确更新。
- 文件移动后稳定 ID 和发布历史不变。
- 重复 ID 被明确识别并阻止发布。

### 32.3 元数据与 AI

- 可以查看并编辑标准元数据。
- AI 返回结构化建议且不会直接覆盖原值。
- 可以逐项接受建议。
- Tags 支持已有词复用、新词创建、数量提示和使用次数参考。
- AI 不可用时可以手工完成审核。

### 32.4 SEO

- 发布前可以看到阻断、建议和可选检查。
- 图片丢失、无效 slug 和元数据缺失能被检测。
- Hugo 构建后的核心 SEO 标签可以验证。

### 32.5 Hugo

- 同一文章重复同步更新同一个 bundle。
- 本地图片被复制并正确重写。
- Taxonomy 和 Hugo build 失败不会标记成功。
- 同步成功后可以打开本地预览。

### 32.6 微信公众号

- 可以预览微信公众号最终样式。
- 可以在至少两个符合相同标准的模板之间切换并得到稳定结果。
- 内置现有样式以 `InkHub Default` 标准模板提供，不在 Provider 中硬编码。
- 本地图片和 Mermaid 能完成处理。
- 可以复制格式化 HTML。
- 复制和人工草稿确认是两个独立状态。
- 文章更新后能够提示草稿可能过期。

### 32.7 数据可靠性

- 数据库迁移前自动备份。
- 应用异常退出不会损坏 Markdown 正文。
- 可重建文章索引，不丢失发布历史。

## 33. 产品风险与应对

### 33.1 范围膨胀

风险：多渠道、AI、SEO、数据库和工作区容易使产品演变成庞大 CMS。

应对：坚持四个主导航、渐进披露和 MVP 渠道限制；任何新增功能必须说明它减少了哪一步真实工作。

### 33.2 AI 破坏 Taxonomy

风险：模型自由生成大量近义或低频 tags。

应对：先召回现有候选和使用次数，再由 AI 排序；用户逐项采用或忽略，并通过全库统计主动调整低频或近义 Tag。

### 33.3 多种 Markdown 约定难以统一

风险：用户 frontmatter、图片目录和链接写法差异较大。

应对：Core 使用统一模型，Source Provider 负责明确映射；MVP 只实现 Obsidian 的常用约定，不承担历史系统兼容。

### 33.4 外部工具依赖

风险：Hugo、Mermaid 和图片上传环境造成安装困难。

应对：核心转换能力内部集成，初始化自动检测、`doctor` 诊断并提供清晰降级；只保留渠道本身必要的外部工具依赖。

### 33.5 渠道规则变化

风险：微信公众号等平台的 HTML 和图片策略变化。

应对：Publish Provider 隔离渠道逻辑，模板标准隔离表现层，提供最终预览和人工确认，不将平台特性扩散到核心模型。

### 33.6 数据与隐私

风险：文章正文发送给第三方 AI 或 Token 泄漏。

应对：本地优先、发送范围可选、Secret 独立存储、日志脱敏、AI 可关闭。

## 34. 产品决策原则

后续面对功能取舍时，按以下顺序判断：

1. 是否解决 Markdown 创作者真实、重复出现的问题？
2. 是否能明显减少发布步骤或错误？
3. 是否可以自动判断，而不增加设置？
4. 是否可以放入现有流程，而不增加主导航和新概念？
5. 是否保持内容源唯一和本地优先？
6. 是否在 AI 或外部渠道失败时仍可使用？
7. 是否属于 MVP，还是可以等待真实需求验证？

如果一个功能增加的理解成本高于节省的操作成本，默认不做。

## 35. 术语表

| 术语 | 定义 |
| --- | --- |
| Source Provider | 读取和写回特定内容源的标准模块 |
| Workspace | 内容源、规则、AI 和发布渠道组成的工作区 |
| Article ID | 不随路径和标题变化的稳定文章标识 |
| Taxonomy | Category、series、tags 及其治理规则 |
| Category | 少量、稳定的主导航分类 |
| Series | 有明确连续关系的一组文章 |
| Tag | 描述主题、技术和概念的跨分类标记 |
| Publish Provider | 将标准文章准备或发布到目标渠道的模块 |
| Content Hash | 标识某一文章内容版本的摘要值 |
| Outdated | 渠道处理版本落后于当前文章版本 |
| AI Provider | 提供 AI 推理能力的本地或远程服务 |
| WeChat Template | 符合 InkHub 标准、可安装和分享的微信公众号样式包 |
